# 重点精读：代码怎样迭代，经验怎样继续使用 

按用户关注顺序整理：Fix Loop → Evolutionary Search → 经验提炼与后续使用。以下区分论文机制与官方发布版具体协议；没有运行论文实验，也未取得完整真实候选演进日志。 

**核心机制：**环境判定任务完成情况，评测脚本统计成绩；Coding Agent 结合程序、trace、图像和已有技能解释失败，写出修改。程序搜索和经验入库主要由提示文件指导 Agent 完成，不是一个自动学习补丁的神经网络。 

## 1．先分清三种“迭代” 

```text
① Fix Loop：51–65执行、诊断、修复 → fix_code.py
→ 在1–50评测，保存修复版成绩
② Evolutionary Search：第一批A保留fix_code.py
→ 8候选×51–65 → 分析并更新task_analysis.md → 下一批
→ 最多5批或开发集达80% → 保存搜索版程序
→ 在1–50评测，保存搜索版成绩
③ 两份定稿程序在66–80比较：成绩高者胜，打平选搜索版
④ 汇总：读取所选版本已有的1–50成绩，不需要重跑1–50
```


**核实边界：**以上针对两份定稿程序和66–80比较结果均齐全的路径。代码中的 val_winner() 使用 ve ≥ vf 时选搜索版；suite_stats() 读取该版本既有测试成绩。发布汇总脚本在选择结果缺失或不全时另有取两版已有成绩最大值的分支，不能将这种分支写成规范的独立选择协议。 


| 层次 | 什么在变化 | 下一步依赖什么 
| Fix Loop：修一个任务 | 一份任务程序不断修正，最终综合成 fix_code.py | 失败种子的执行证据、已有成功行为、已有技能 
| Evolutionary Search：探索多种策略 | 每轮一批不同假设的候选程序 | 强候选的代码、残余失败、持续更新的 task_analysis.md 
| 跨任务积累：复用修复经验 | 共享技能文件中新增或合并经验 | findings.md、有效代码片段、来源和开发集证据  

三者可以串起来：已有技能帮助当前任务生成初始程序；Fix Loop 先做定向修复；困难任务再做多候选搜索；有依据的通用经验经协调者整理后，供后面的任务使用。并非每个任务都必须完成全部环节。 

## 2．Fix Loop：程序失败后，具体如何修改？ 



观察场景
读取已有技能→

写 initial_code.py
执行开发种子→

诊断失败
编写并回放修复→

综合 fix_code.py
写 findings.md 

**起点：**当前发布版 LIBERO Fix Loop 要求先观察一份场景、读取相关共享技能，保存场景图与任务分析，再由 Agent 写 initial_code.py；不要求使用外部基线。先在 seed 51 做冒烟检查，再在 51–65 上执行初始程序。初始场景理解只是待检验假设，不能硬编码那个场景的物体坐标或 mask 排序。 

**诊断：**Actor 查看失败种子的 code.py、trace.json、summary.txt 与相关关键帧。它要回答“原本想做什么、实际做到了哪里、最早出现的异常是什么、哪些后续失败只是连带结果”。例如，分割有结果但导航反复规划失败，就应先检查接近位置；夹爪已经夹住却在运输中掉落，则检查抓取稳定性与运输轨迹。 

**修改：**Actor 根据根因假设编辑 Python 程序，允许改变提示词、对象消歧、坐标转换、抓取姿态、路点、动作顺序或恢复策略。没有固定的错误分类器自动输出补丁，也不保证每次只改一行。先在失败开发种子上回放，失败就继续读新证据；还要保留其他种子依赖的成功行为。 

**收尾：**综合不同种子的证据，选择一个任务级 fix_code.py，禁止按种子编号分支。当前 Fix Loop 提示规定每个开发种子最多3次失败修复回放，耗尽后记录阻塞原因；这项上限与 Evolutionary Search 的“8候选×5批”是不同预算。若没有完全成功方案，也要如实保留当前最强合法程序与失败说明。 

代码核对：.claude/libero/fix-loop/subagent-prompt.md，Stage 0 / Stage 1。当前发布版由 Actor 完成开发阶段，Coordinator 运行留出评测；不要把附录旧提示中的所有分工当作现版行为。 

## 3．谁判断成功：环境、评测脚本和 Agent 各做什么？ 

```text
# evosearch_eval.py 的关键逻辑节选
_, reward, terminated, truncated, info = env.step(code_str)
task_completed = bool(info.get("task_completed", False))
...
pass_count = sum(r["task_completed"] for r in trial_results)
pass_rate = pass_count / n_trials_run
```


**环境**返回任务完成标记；**评测脚本**据此计算成功数与成功率，并另外记录 reward、崩溃和耗时；**Agent**解释失败并提出修改。退出无报错不等于任务成功，图上“看起来差不多”也不代替评测标记。机器人候选代码不得读取隐藏成功谓词或仿真真值；环境内部用于评测与候选程序可访问的信息要分开。 

8个候选都分别在 seed 51–65 上执行：每批120次主要候选评测。最多5批就是600次；若某批完成后有候选达到12/15（80%），工作流标记 SOLVED，停止继续生成下一批。SOLVED 只表示达到开发集搜索阈值，不等于对未见场景保证成功。场景快照、诊断回放、Fix Loop、选择集和最终评测另计。 

代码核对：scripts/libero/evosearch_eval.py:156–159、564–587；evosearch/subagent-prompt.md 的停止规则。 

## 4．Evolutionary Search：一轮到下一轮的完整过程 

### 步骤A：确定任务、读技能、保留已有程序 

读取实际运行时任务指令，防止文件名与重映射目标不一致；读 localize.md、grasp.md、transport.md、manipulation.md 以及适用的搜索伴随技能。第一轮将已有 fix_code.py 原样作为 candidate_A，保留一个可比较的性能参照，并在 task_analysis.md 中记录其来源。 

### 步骤B：把当前理解写成“可被执行证伪的假设” 

观察全景和腕部视角，记录物体形状、接近与抓取策略、目标几何、移动与放置策略，以及不确定之处。比如：“目标后方看起来被架子挡住”仍是视觉假设；“某种抓法不行”必须有执行依据，不能仅靠想象排除。 

### 步骤C：写8个候选，每个代表不同的修复假设 

候选文件头写明 Hypothesis、Differs from prior、Expected failure if wrong、Seeded from。工作流要求候选检验不同假设，避免8份程序只在同一处做微小参数变化。可改变的是程序策略本身，例如抓取方向、定位方法、动作顺序和接触方式；不是对 LLM 权重做更新。 

### 步骤D：固定种子执行，得到可比较的结果 

各候选使用相同的15个开发种子。每个种子保存 code.py、trace.json 和 summary.txt，候选结果汇入 eval_results.json，全批结果汇入 iter_summary.json，主要按 pass_rate 排名，另外展示错误数和 reward。 

发布版批量评测为加速会清空缓存关键帧与数组后保存 trace，因此不能假设每个批量 trial 都有完整视频和关键帧。需要视觉诊断时，额外回放选定成功/失败试验；工作流的 --no-highlights 会跳过自动精彩回放。 

### 步骤E：分析全部候选，而不只看最高分 

Agent 阅读排行榜、调用日志与补充回放，判断每个策略在哪个阶段失败。低分候选也可能暴露一种有用技术，高分候选也可能在一个固定几何条件下反复失效。仅用“成功率低”解释失败，不能指导下一轮代码修改。 

### 步骤F：更新 task_analysis.md，再写下一批 

更新场景理解与几何假设，追加候选策略、成绩、证据、已排除方向和未解问题。随后从 Top-3 强候选出发改写下一批程序。论文算法使用历史程序集合的 Top3；官方主提示写当前轮强候选，伴随技能允许从以往各轮 Top-3 获取起点。共同原则是复用强程序及其残余失败，而不只盯着单个赢家。 

**这是语义层面的继承和重写：**Agent 可以保留候选B有效的定位方式，同时采用候选C的运输策略，或提出新动作顺序；没有固定逐行交叉或随机变异算子。提示还要求至少一个候选在结构上区别于此前各轮，以免整个群体陷入同一种思路。 

### 步骤G：停止、保存最佳方案，再做独立评测 

达到80%或耗尽5批后停止搜索，保存 evosearch_best_code.py。工作流要求在开发表现未胜过原修复程序时保留较强参照；不是无条件采用最后一轮新程序。LIBERO-Pro 最终 Fix/Evo 方案选择使用66–80，最终报告使用1–50；这些种子不能用于逐轮修复。发布提示、选择脚本与论文表格之间的执行顺序仍需区分，汇总结果本身不足以审计全部历史。 

来源：论文算法1；evosearch/subagent-prompt.md:85–285；evosearch/skills/evosearch-iteration.md §2、§4、§7–9；evosearch_eval.py:176–210。 

## 5．看一次“成绩 → 解释 → 下一轮代码”的转化 

下面是教学示意，场景和成绩用于说明工作流；不是论文真实候选演进日志。为简洁仅列出8个候选中的3个。 


| 第一批候选 | 示意成绩 | 发现的证据 | 下一轮可检验的修改 
| A：原修复程序 | 7/15 | 抓住碗后，斜向运输碰到高障碍 | 保留定位与抓取，改成先上升、再横移、再下降 
| B：更安全运输路径 | 10/15 | 运输改善，但夹爪遮挡目标，导致放置定位不稳 | 在关键状态重新观察；检验可见视角，而非沿用过期目标位置 
| C：侧向接近 | 3/15 | 还未接触目标就受机械臂姿态约束 | 暂记“受阻、未真正检验”；若找到姿态调整技术，再组合重试  

下一轮可以从B出发改目标观察，从A出发测试另一种运输结构，并用新姿态重试C。这样每份新程序都有明确的起点、证据与假设，不是把失败代码重新交给模型后笼统说一句“再试试”。 

```text
# task_analysis.md 的示意更新
## iter_00
强候选：B（10/15）；剩余问题：目标在运输后被遮挡。
已排除：未经抬升直接斜向跨越高障碍的路径。
受阻但未检验：侧向接近；尚未结合机械臂姿态调整。
下一轮：测试重新观察、另一运输结构、姿态调整后的侧向接近。
```


“已排除”和“受阻但未检验”必须分开。官方 cross-reference rule 要求：发现新技术后，回看受阻清单，判断哪些旧假设值得重新尝试。经验因此能在同一次搜索里组合使用，而不只是任务结束后才入库。 

## 6．经验保存在哪：四种文件对应四个范围 


| 文件 | 谁写 / 何时写 | 保存什么 | 谁再使用 
| trace.json / summary.txt / 执行产物 | 运行与评测代码，每次 trial | 实际调用、结果、错误、耗时；视觉产物按运行模式保存 | 当前 Actor 诊断与补充回放 
| task_analysis.md | Actor，搜索前建立、每轮更新；Fix Loop 也有初始分析 | 场景理解、假设、成绩、淘汰依据、待检验分支 | 同一任务后续轮次的候选生成 
| findings.md | Actor，任务开发阶段或搜索阶段收尾 | 根因、有效修改、开发证据、阻塞项、可泛化模式；评测结果单列 | Coordinator 审查与技能晋升 
| 共享 skills/*.md | Coordinator，审查后合并更新 | 触发条件、有效代码片段、适用边界、来源与成功证据 | 后续任务、新搜索轮次及迁移评测的 Agent  

**task_analysis.md 是任务内工作记忆；findings.md 是任务级交接报告；共享技能是跨任务持久记忆。**三者有联系，但不能把同一个文件名当作所有经验存储的统称。 

## 原始字段怎样串起下一轮与经验交接（用户确认保留） 

**task_analysis.md：**1. Object Shape；2. Grasp/Approach Strategy；3. Goal Geometry；4. Placement/Movement Strategy；5. Hypotheses for iter_00；6. Iteration Log。前五项记录当前任务理解与初始假设，执行后根据证据修订。 

**Iteration Log：**Open questions going in 说明本轮要检验什么；Results 表按 Candidate / Strategy / Pass rate / Status 记录候选与结果；Eliminated 记已否定方向；Blocked, untested reconfiguration 记受阻但尚未结合姿态调整检验的方向；Geometry updates (cite keyframe/trace) 记录有证据的场景认识变化；Open questions → iter_01 提出下一轮问题。 

**Fix Loop 的 findings.md：**Root causes observed 记录根因及受影响种子；What fixed them 记录有效修改及哪些种子从失败变成功；Generalizable patterns 记录可跨任务使用的模式；Blocked seeds 记录仍未修好的种子与原因。 

**Generalizable patterns 的内部字段：**Trigger（适用症状或条件）、Code（有效程序提取的5–20行代码，泛化任务专属提示与常数）、Evidence（哪些开发种子被修好）、Target skill file（localize.md / grasp.md / transport.md / manipulation.md）。 

**Coordinator 入库后的默认小节：**Trigger + Code + Why it works + evidence；后者附源suite/task、开发种子、fix_code.py来源路径与日期。实际技能文件还可能采用专用表格或辅助函数，并非统一机器可解析schema。 

```text
Results + Geometry updates + Eliminated / Blocked...
+ Open questions → iter_01
↓
下一轮候选程序
↓
findings：What fixed them + Generalizable patterns
↓
共享技能：Trigger + Code + Why it works + evidence
↓
后续Agent读取 → 判断适用性 → 编辑新任务程序 → 执行检验
```


字段对照官方evosearch-iteration.md任务分析模板、fix-loop/subagent-prompt.md findings模板、fix-loop/main-agent-prompt.md §6；选择逻辑见plot_method_comparison_v5.py:63–113。 

## 7．最重要的环节：修复怎样变成后续可用的技能？ 

### ① Actor 先报告可复用部分，并附上代码和证据 

当前 Fix Loop 的 findings 格式要求，每个可泛化模式给出 Trigger、从 fix_code.py 提取的5–20行有效代码、哪些开发种子由失败变成功，以及建议写入哪个技能文件。若没有能跨任务使用的部分，明确写 none。整段成功任务程序不会因为“成功过一次”就自动变成通用技能。 

### ② Coordinator 阅读报告，提炼条件与适用范围 

协调者也是 Coding Agent 角色，由提示指导其判断；它不只是运行一个确定性的复制脚本。Coordinator 读 findings，必要时核对修复程序，检查可复用性与允许 API，去掉场景专属坐标或仅适用于某个种子的分支。保留可复现的代码模式、失败触发条件与证据来源。 

### ③ 按主题合并进技能文件，保留证据与边界 

定位提示与消歧进入 localize.md；抓取与夹爪验证进入 grasp.md；路点与运输进入 transport.md；抽屉、旋钮、推动等进入 manipulation.md。已有同类经验就扩展原章节，加入新证据或标注变体，避免重复追加或静默替换有效策略。 

```text
# 新增技能的结构示意，不是实际新增的论文技能
## 搬运前先清障，再横移
Trigger：夹持后斜向运输与高障碍碰撞。
Code：提取已验证的升高 → 横移 → 下降代码，参数由当前观测计算。
Why + Evidence：来自哪个任务、修复了哪些开发种子、代码来源与日期。
Boundary：抬升是否可达、目标上方是否有障碍，仍要在新任务检查。
```


### ④ 晋升脚本记录变化，但不替代科学判断 

当前 Fix Loop 发布版使用 record_skill_promotion.py：begin 保存更新前快照，Coordinator 实际编辑技能文件，finish 保存补丁、哈希和 JSONL 记录，verify 检查晋升记录。没有通用经验时可记录原因而不改库。**审计脚本能追踪“改了什么”，不能自动证明新经验在所有任务都有效。**明确规则是仅用开发阶段证据驱动技能修改，留出结果单独报告。 

代码核对：fix-loop/subagent-prompt.md 的 findings 格式；fix-loop/main-agent-prompt.md §6；scripts/libero/record_skill_promotion.py。 

## 8．后续任务怎么“用经验”：读文件 → 选策略 → 改写新程序 → 再检验 



任务A执行发现
一条有效修复→

findings
Coordinator合并技能→

任务B读取技能
结合当前场景选择→

写B的新程序
执行、诊断、再修 

**读取：**官方 LIBERO 搜索提示显式读取4个共享技能文件，LIBERO-90 子任务提示也要求先读库。论文称为 retrieval / in-context guidance；已查阅的具体工作流通过文件读取与相关伴随技能实现，不应补写成一个未核实的向量数据库或固定相似度检索模型。 

**使用：**Agent 将当前症状与技能 Trigger 对照，选择适合的代码模式，修改对象提示、坐标、姿态和参数，写进新任务程序。代码片段成为生成上下文，不会仅因技能文件存在就自动运行。普通新任务可执行并继续修复；零样本留出实验则只生成一次，不再调试或更新库。 

**举例（机制示意）：**任务A学会“运输先升高再横移”。任务B要把另一物体送入容器，Agent 可以复用运输结构，但必须按B的观测计算位置，检查容器边缘和可达空间。若B在下降阶段失败，应更新B的任务分析，而不是宣称A的经验在所有场景都无效；成功的进一步修复再按证据决定是否扩展共享条目。 

**同一任务内也复用经验：**下一批先读 task_analysis.md，复用Top-3的有效片段；发现新技术后重新检查受阻分支。跨任务则靠共享技能文件把这种经验带到全新的 Actor 上下文，不需要把A的全部聊天或轨迹复制给B。

## 9．不要混淆两个具体协议：LIBERO-Pro搜索与LIBERO-90建库 

上面的8候选×15种子×最多5批，是 LIBERO-Pro Evolutionary Search 的具体搜索设置。用来研究“经验越多是否越强”的 LIBERO-90 建库采用另一套发布流程：90任务固定顺序，每批5个任务，开发种子51–80，每批任务完成后协调者集中审查 findings，更新技能并保存 Git 快照，再开始下一批。 


| LIBERO-90建库提示中的审查规则 | 含义与边界 
| 经验报告成功率至少15/30 | 作为该协议的可靠性门槛；涉及修复禁用API邻近失败的模式有明示例外。不是所有ASPIRE流程统一门槛。 
| 替换有效旧模式需至少高10个百分点 | 不够时标成备选，并保留各自成绩；不是静默覆盖。 
| 拒绝场景过拟合常数 | 不把绝对XY、单场景颜色阈值等当成可泛化经验。 
| 有望帮助至少两类任务 | 这是入库判断要求，不等于已经在两类独立任务上完成验证。  

该流程每5任务存一次 snapshot-N5、snapshot-N10…，后续任务继承已更新的库。同一批任务通常从该批开始时的库出发，下一批才明确继承本批汇总经验。迁移评测使用冻结的库快照，不能把评测任务失败修复后再计为零样本。 

代码核对：zeroshot-transfer/main-agent-prompt.md，Core Loop、Review findings + update skills。这里只描述原项目的保存机制；本次未执行任何训练、实验或Git提交。 

## 10．归纳：代码进化与经验进化是两条相接的链 

**代码链：**初始程序 → Fix Loop定向修复 → 多假设候选 → 固定配置执行 → 成绩与证据 → 更新任务分析 → 继承强候选并重写 → 保存最佳程序。 

**经验链：**实际修复证据 → findings结构化报告 → Coordinator审查与泛化 → 合并技能代码与适用条件 → 记录版本 → 后续Agent读取 → 写新任务程序并检验。 

最值得关注的“迭代算法”分工：评测器提供可比较的结果，日志保留可定位的证据，task_analysis 保留任务内推理进度，Coding Agent决定下一轮改什么，findings与技能库把有依据的修复带到后续任务。
